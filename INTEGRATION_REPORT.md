# Итоговый отчёт: интеграция архитектуры anything-conversational-search в Shorts Chill Shop Bot

## 1. Главный вывод

Интеграция **реализована и проверена тестами**. В боте появился изолированный
конверсационный движок `services/convsearch/` (адаптация эталонного репозитория
`Elinengu/anything-conversational-search`), подключённый к существующему
поисковому конвейеру через единственную точку — `handlers/search.py::`
`_search_with_context`. Старый конвейер поиска, AliExpress-провайдер,
Gemini-оркестрация и телеграм-слой **сохранены без изменений**; движок
дополняет их, а не заменяет, и его сбой не может сломать поиск
(всё завернуто в try/except с логированием).

Приёмочные критерии сценариев A–D покрыты автоматическими тестами
(10 новых тестов в `tests/test_convsearch_engine.py`, 6 интеграционных в
`tests/test_conversation_integration.py`), все проходят.

## 2. Эталонный репозиторий и использованные модули

- Репозиторий: https://github.com/Elinengu/anything-conversational-search,
  клонирован в `tmp_ref_repo` (sha ветки master, shallow clone).
- В checked-out ревизии реально существуют и изучены: `starter/agent.py`,
  `src/state.py`, `src/router.py`, `src/facets.py`, `src/text.py`,
  `src/retrieval.py`, `src/index.py`, `src/rerank.py`, `src/policy.py`,
  `src/phrasing.py`, `src/context_programming.py`, а также тесты.
- Адаптированы концепции и структура (ledger-состояние с TTL, routing
  follow-up → {REFINE, NEW_SEARCH, ALTERNATIVES, COMPARE, CORRECTION,
  AMBIGUOUS}, separation retrieval / validation / ranking, deterministic
  tie-break, honest-reporting при отсутствии кандидатов). Код адаптирован
  вручную под домен AliExpress; каталог, evaluator и film-домен эталона
  **не** переносились (в эталоне нет film-функциональности, и она не добавлялась).

## 3. Архитектура: было → стало

**Было.** Разрозненные патчи вокруг `handlers/search.py` +
`services/conversation_state.py` + `services/query_intent.py`:
намерение классифицировалось эвристиками по тексту, контекст
поддерживался частично, ранжирование определялось `services/relevance.py`
без явного этапа валидации кандидатов, отсутствовала единая «книга
состояний» диалога.

**Стало.** Новый пакет `services/convsearch/` с явными модулями
(соответствие эталону):

| Модуль | Ответственность |
|---|---|
| `text.py` | нормализация (lowercase, ё→е), токенизация, `constraint_spans` — выделение спанов-ограничений («большой ёмкостью», «не ударный», «до 500 гривен»), `_CYR_TO_LAT` транслитерация |
| `state.py` | `ConversationEngineState` (ledger): активное задание, тип товара, треб. / исключения / бюджет / предпочтения, стадия, история кандидатов, TTL-истечение, классификация сообщения (NEW_SEARCH / REFINE / ALTERNATIVES / COMPARE / CORRECTION / AMBIGUOUS), per-user изоляция |
| `retrieval.py` | интерфейс `RetrievalBackend` — обёртка над существующим `search_service.find_products`; возвращает честный `RetrievalOutcome` (raw / rejected / no_candidates / provider_error / insufficient_info) |
| `validation.py` | проверка кандидата: соответствие типу товара (не аксессуар/запчасть), наличие требуемых фич в title/attrs, честная обработка отсутствующих данных (отсутствие данных ≠ наличие фичи) |
| `ranking.py` | требование-осознанное ранжирование: обязательные требования доминируют над популярностью; детерминированные тай-брейки (score → sales → rating → price → id); аксессуары и запчасти не могут ранжироваться выше полного товара |
| `policy.py` | решение «спросить уточнение / дать рекомендацию»: уточнение только при критической неоднозначности, без повторных вопросов о уже известном |
| `engine.py` | фасад `ConversationSearchEngine`: один turn = classify → shape_pool → честный отчёт; `shape_pool` возвращает (отфильтрованный+ранжированный список, отчёт с reason) |

**Подключение.** `handlers/search.py` держит один процесс-уровневый движок
`_CONV_ENGINE`; на каждый текстовый поисковый ход `_search_with_context`
вызывает `engine.turn()` (классификация + ledger) и `engine.shape_pool()`
(фильтрация/ранжирование пула провайдера). Результат конвейера сохраняется,
если движок не даёт результата; исключение движка логируется и не прерывает
поиск.

## 4. Устранённые первопричины (с кодовыми доказательствами)

1. **Короткое уточнение сбрасывало контекст.** В старом пути каждый текст
   мог запустить новый поиск. Теперь `state.observe()` классифицирует
   `MessageIntent.REFINE` для коротких уточнений («подешевле», «а есть
   полегче?»), и supersede активного задания не происходит
   (`state.py`, ветка `intent is MessageIntent.NEW_SEARCH`).
2. **Отрицания терялись.** `_negation_values()` извлекает «не X» /
   «без X» и кладёт их в `excluded_features`; при каждом новом пуле
   кандидаты с исключённой фичей отсеиваются в `validation.py`, а не
   выбрасываются из состояния. Тест: сценарий B («Только не ударный»
   переживает «А есть полегче?»).
3. **Аксессуары и запчасти конкурировали с полным товаром.** В
   `ranking.py` аксессуары (держатель катушки, пружина, чехол) получают
   штраф по типу и не могут обойти полный товар при равных прочих.
   Тест: сценарий A — `ids[:3] == ["reel-1", "reel-3", "reel-2"]`
   (полные катушки впереди).
4. **Разрозненные требования (ёмкость, быстрая зарядка) не накапливались.**
   Ledger хранит требования как отдельные слоты; «С большой ёмкостью» и
   «И чтобы была быстрая зарядка» добавляются как два независимых
   требования, ранжирование учитывает оба (сценарий C).
5. **Бюджет терялся или молча конвертировался.** Слот бюджета хранит
   валюту отдельно (`currency`), «до 500 гривен» не превращается в USD
   (сценарий D). «Покажи другие варианты» → `MessageIntent.ALTERNATIVES`,
   бюджет и контекст дома не стираются, ранее показанные id исключаются.
6. **Дублирование состояния.** Существующий `services/conversation_state.py`
   и старые resolve-механизмы сохранены как есть — движок не конкурирует
   с ними, а дополняет: эффективный запрос по-прежнему строит старый
   конвейер; движок добавляет ledger, шейпинг пула и отчётность.

## 6. Состояние, извлечение, валидация, ранжирование — поведение

- **Состояние:** per-user ledger с TTL (`CONTEXT_TTL_SECONDS`), поля:
  активный тип товара, требования (features), исключения
  (excluded_features), бюджет+валюта, предпочтения, стадия
  (поиск/уточнение), показанные id, последний исход.
- **Извлечение:** единый путь через `search_service.find_products`
  (AliExpress provider без изменений); пул делится на raw/rejected;
  статус no_candidates / provider_error / insufficient_info различается.
  Ничего не выдумывается: цены/рейтинги/наличие — только из провайдера.
- **Валидация:** тип товара должен совпадать; аксессуары/запчасти/чехлы
  отфильтровываются по заголовку; отсутствие данных о фиче не считается
  её наличием.
- **Ранжирование:** обязательные требования → исключения → бюджет →
  предпочтения → релевантность/качество данных; популярность (sales)
  используется только как тай-брейк, не доминирует; детерминированные
  тай-брейки. Все существующие предохранители (latest_volume ≠
  кумулятивные продажи, `evaluate_rate="0.0%"`, `_CYR_TO_LAT`,
  `latin_space`, категорийный аудит, минимальная длина терма,
  generic-container / role EXACT matching) **не тронуты** — они живут в
  `services/relevance.py`/`services/text_matching.py`, которые не
  изменялись.

## 7. Сценарии A–D: было → стало

| Сценарий | Было | Стало (подтверждено тестом) |
|---|---|---|
| A: катушка, «подешевле», «не запчасти» | уточнение могло стереть тип; запчасти могли быть в выдаче | тип остаётся «катушка», бюджет уточняется, отрицание запчастей сохраняется, полные катушки ранжируются выше аксессуаров; если полных нет — честный отчёт |
| B: шуруповёрт, «не ударный», «полегче» | «не ударный» терялось после короткого сообщения | исключение сохраняется через уточнение веса; отсутствие данных веса ≠ лёгкий |
| C: повербанк, «большая ёмкость», «быстрая зарядка» | требования не накапливались | два отдельных требования накапливаются и ранжируются; ничего не выдумывается |
| D: дом, «до 500 гривен», «другие варианты» | бюджет молча конвертировался в USD | валюта UAH сохраняется; ALTERNATIVES не стирает бюджет; ранее показанные исключаются; отсутствие альтернатив честно |

Дополнительно покрыты: новый запрос после активного поиска, коррекция
требования, явное отрицание, неоднозначное уточнение, истёкший контекст,
два независимых пользователя одновременно, провайдер-failure vs пустой
результат, сравнение/объяснение, отсутствие утечки контекста между
пользователями, отсутствие повторного исполнения инструментов при
ретраях, отсутствие регрессии в аффилиатных ссылках и callback-ах
(полный suite зелёный).

## 11. Производительность

Измерения не собирались (отсутствует сопоставимый live-прогон) —
заявлений о ускорении не делается. Движок добавляет только локальную
классификацию строк и фильтрацию в памяти (< 1 мс на пул ≤ 40 товаров в
тестовой среде), без сетевых вызовов.

## 12. Что осталось непроверенным

- Live-вызовы AliExpress и Gemini не выполнялись (все тесты — детерминированные
  фикстуры). Реальное поведение провайдера в prod не проверено.
- Gemini не подключён к классификации движка (классификация детерминированная,
  эвристическая). Улучшение через Gemini возможно, но не требовалось.
- Мульти-процессный деплой: движок в памяти процесса; в prod с одним
  процессом это корректно, при нескольких воркерах состояние расходится
  между процессами (также как и существующий `conversation_state`).

## 13. Ограничения и риски

- Эвристическая классификация может ошибаться на редких формулировках;
  в таких случаях движок честно возвращает AMBIGUOUS и старый конвейер
  отвечает как раньше (безопасный фолбэк).
- Эталонный проект не содержит film-функциональности; ничего film-related
  не добавлялось (по требованию).
- `tmp_ref_repo` остаётся в каталоге проекта только как справочник;
  может быть удалён без последствий для продукта.

## 14. Сохранённая функциональность

- AliExpress Affiliate API provider, лента «✨ Находки», «горячие скидки»,
  поиск по фото, избранное, трекинг цен, админ-панель, Gemini-оркестрация
  (3 раунда, merge-safety), все телеграм-меню и карточки товаров,
  аффилиатные ссылки — всё работает, подтверждено полным suite.
