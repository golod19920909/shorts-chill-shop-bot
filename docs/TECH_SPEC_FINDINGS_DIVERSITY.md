# Техническое задание: разнообразие и полнота «✨ Находок»

Дата: 2026-11-10  
Репозиторий: `golod19920909/shorts-chill-shop-bot`  
Рабочая ветка: `audit/aliexpress-portals-smoke-test`

## 1. Проблема

После восстановления пагинации лента успешно получает 100 реальных товаров (две страницы по 50), но фактическая подборка содержит только 19 позиций и заметно смещена в одну узкую тему: средневековые аксессуары и товары для косплея.

Причина состоит из двух частей:
- две соседние страницы широкого каталога могут оказаться близкими по тематическому составу;
- Gemini может вернуть меньше 20 ID, а текущая постобработка применяет семейный лимит только к выбранным ID и не использует оставшийся реальный пул для безопасного заполнения.

## 2. Цель

При каждом открытии «✨ Находки» получать до 20 интересных, максимально разнообразных карточек из реальных товаров AliExpress. Если в собранном пуле достаточно разных подходящих товарных семейств, выдача должна содержать 20 карточек. Если каталог объективно не даёт такого разнообразия, не нужно искусственно заполнять список сомнительными повторами.

## 3. Получение кандидатов

1. Источник остаётся прежним: только официальный AliExpress Affiliate API `aliexpress.affiliate.product.query`, без ключевых слов и без искусственной сортировки.
2. Сохраняется действующий лимит API-запросов на одно открытие: по умолчанию не более двух страниц, максимум определяется существующей настройкой `FEED_MAX_PAGES_PER_OPEN`.
3. Вместо двух соседних страниц использовать разнесённую выборку. При стандартном бюджете последовательность открытий: 1/40, 2/41, 3/42 и далее.
4. Шаг 39 опирается на зафиксированную live-проверку: страницы 1, 2 и 40 не имели общих ID. Это расширяет выборку без увеличения количества запросов, но не обещает тематической независимости любых страниц.
5. Курсор хранит базовую страницу и увеличивается на 1 за успешное открытие. При API-ошибке сохраняется base page текущего открытия, чтобы следующий запуск повторил ту же выборку.
6. Если первая запрошенная страница с base page выше 1 подтверждённо пуста и кандидаты ещё не собраны, разрешено восстановление с page 1 в оставшемся бюджете. Ошибка API не считается пустой страницей.
7. Пустая дальняя выборочная страница (например, page 40) сама по себе не означает конец каталога и не сбрасывает курсор.
8. Сохраняются технические проверки изображения/партнёрской ссылки, canonical dedup, исключение уже показанных пользователю товаров и отдельная история `FLOW_FEED`.

## 4. Отбор и заполнение

1. Использовать существующий `AIService.select_findings_candidates`, текущую Gemini-модель, таймаут и телеметрию. Не менять общую модельную конфигурацию и обычный поиск.
2. Передавать Gemini реальные ID, название, category_path и существующие allowlisted коммерческие сигналы.
3. Усилить правила отбора: широкий охват категорий и назначений; учитывать `category_path` вместе с названием; избегать нескольких вариантов одного семейства, если есть другие подходящие семейства.
4. Не превращать отсутствие рейтинга, заказов, скидки или промокода в автоматический отказ. Не вводить жёсткие пороги цены, рейтинга или заказов.
5. Если в пуле не менее 20 технически пригодных разных товаров, Gemini должен выбрать ровно 20 лучших доступных ID.
6. Gemini по-прежнему возвращает только ID. Любые неизвестные ID отбрасываются.
7. Если Gemini вернул меньше 20 валидных ID, выбранные ID остаются в начале; оставшиеся кандидаты ранжируются только по реальным сигналам AliExpress и проходят через существующий `family_select`. Это позволяет безопасно заполнить выдачу из того же пула.
8. При недоступности Gemini, таймауте или некорректном ответе сохраняется детерминированный fallback.
9. Максимум остаётся 20 карточек. Если реальных подходящих разных семейств меньше, допустима более короткая выдача.

## 5. Аналитика и диагностика

- Сохранить счётчики кандидатов, exact/near duplicates, результата Gemini, числа выбранных карточек и времени curation.
- Логи должны позволять понять, какие страницы были запрошены и сколько карточек прошло финальный отбор.
- Не логировать ключи, подписи, секреты и приватные параметры запроса.

## 6. Что запрещено менять

- Обычный поиск, поиск по фото, категории и диалоговый Option C.
- Модель Gemini, primary/reserve, таймауты и общие настройки AI.
- Схему БД, историю просмотра, Telegram UI, цены, скидки и партнёрские ссылки.
- AliExpress endpoint и число запросов на одно открытие.
- `.env`, ключи и локальную базу.
- `main`, PR №10 и другие ветки.

## 7. Проверки и приёмка

Только офлайн-тесты с fake/stub, без реальных Gemini, AliExpress или Telegram:
1. Выборка страниц: 1/40, затем 2/41; бюджет в один запрос даёт одну страницу.
2. Курсор увеличивается на 1; API-ошибка сохраняет base cursor для повтора.
3. Пустая дальняя страница не сбрасывает курсор и не объявляет весь каталог исчерпанным.
4. Восстановление stale cursor остаётся в рамках исходного лимита запросов.
5. Короткий AI-список заполняется только реальными кандидатами из того же пула, с приоритетом новых семейств.
6. Неизвестные ID Gemini отбрасываются; near-duplicate и family selection продолжают работать.
7. Gemini prompt требует широкого охвата категорий и ровно 20 ID при достаточном пуле.
8. Обычный поиск и другие discovery-потоки не меняются.

После локального pull нужен smoke-тест с приватным `.env`: проверить реальные страницы, число и тематическое разнообразие карточек. Успех офлайн-тестов не заменяет live-проверку.

## 8. Отчёт

Указать изменённые файлы, commit, точные тестовые команды и результаты. Не заявлять live API-проверку до запуска обновлённого бота с пользовательскими credentials.
